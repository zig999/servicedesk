Scope: frontend target (frontend/app) — implement, on the presentation side, the same three specification nodes already implemented on the backend side in this same initiative (see epic/draft-correction-while-invalid.md and epic/draft-discard-while-invalid.md for what the backend delivers: a read-case-version operation returning a draft's own declared attributes without validating it, HTTP 200; and update-draft answering with those same attributes after the write, also without depending on validation).

1. rules/knowledge/a-presented-case-version-offers-a-route-to-its-own-editing-surface-on-every-reading — a surface presenting one case version (by slug + number) offers the curator a route to that same version's own editing surface on every reading of that surface, including one refused by CaseVersionNotValidError.

2. rules/knowledge/an-editing-surface-presents-a-drafts-own-declared-attributes-even-when-that-draft-does-not-read-back-as-a-case — a draft case version's own editing surface presents title, when_to_use, subject, fallback and consolidation_register exactly as the draft's own stored record carries them (using the backend's new read-case-version endpoint, not read-case, which keeps refusing), stating explicitly when consolidation_register is absent, and accepts submission of update-draft over them, on a reading where the version was refused because some validator rule of validation-runs-at-every-read does not hold for it.

3. rules/knowledge/a-discard-is-offered-and-accepted-while-its-drafts-current-read-does-not-answer-a-case — a surface presenting a draft case version offers the curator the act of discarding it, even when the version does not validate. The backend already accepts this (no backend change was needed there); only the frontend needs to offer the control in that state.

Implementation context already investigated this session (frontend is frontend/app/src/):

- frontend/app/src/routes/case-version-editor-screen.tsx:38-47 — today, when `state.phase === "not-valid"`, renders only "This case's current version does not read back as a case." with a link to "Manifest" — no Save/Cancel/Discard control at all.
- frontend/app/src/hooks/use-edit-draft-version-form.ts:252-253 — sets `phase: "not-valid"` whenever the version-load query errors with `versionErrorKind === "case-not-valid"` (mapped from CaseVersionNotValidError in frontend/app/src/services/error-ui-state.ts:60).
- frontend/app/src/routes/case-version-editor-ready-view.tsx — the "ready" view (when the read succeeds) already has the full form with title/when_to_use/subject/fallback/consolidation_register fields, a "Save changes" submit button, "Cancel", and a "Discard draft" dialog at roughly lines 188-235, gated by `discard.canDiscard`.
- frontend/app/src/hooks/use-edit-draft-version-form.ts:337 — `canDiscard: record.state === "draft" && !isReleased` — this gate does NOT depend on version validity, only on its state; it is never reached today for an invalid version because the phase never reaches "ready" in that case.
- The "Manifest" screen (frontend/app/src/routes/version-manifest-screen.tsx) and the "New Hypothesis" flow already work even when the version's read is refused — verified by running the app in Chrome earlier this session.

What the frontend work the three rules require comes down to: when read-case fails with case-not-valid, the screen must stop falling back to the "not-valid" state that blocks everything. Instead it should call the backend's new read-case-version endpoint (which returns the draft's attributes without requiring validity) and render the same CaseVersionEditorReadyView used for a valid version, with a non-blocking warning banner stating that the current version does not pass validation — keeping Save changes, Cancel and Discard draft available. The form's submit (update-draft) will already work in this state once the backend delivers its corresponding task, since the backend will also answer 200 with the attributes after the write instead of throwing CaseVersionNotValidError.

Do not decide the exact visual details of the warning banner (color, exact copy, placement) — that is form and is left to implementation, as long as it clearly communicates that the current version does not pass validation, distinct from any other state.
