---
type: invariant
statement: A curator whose create-draft submitted from a case-authoring surface succeeds is taken to the created case version's own surface — the one addressed by the case's own slug together with the version number that creation assigned, which read-case answers for that slug and that version, the version number being the one the completed creation itself names rather than one the surface derived — and never to the listing of cases, to that case's own versions listing, or to the authoring surface the creation was submitted from.
expression: For every create-draft submitted from a case-authoring surface that succeeds, creating version v of case c, the curator's destination is the surface keyed on c's own slug together with v's own version number as the completed creation names it; that destination is never the cases listing, never c's versions listing, and never the authoring surface the submission was made from.
constrains:
  - domain/knowledge/case-version
---

## Description

A create-draft that succeeds leaves a draft version standing at the case's own slug and at the number that case's next_version counter assigned it, so the destination keyed on that identity is one that answers — the same reading a-successful-capability-registration-lands-on-the-capabilitys-own-surface and a-successful-connector-registration-lands-on-the-configurations-own-surface each gave for their own registry, where a success removes exactly the unanswerable read an abandonment leaves behind. That is also why this landing and an-abandoned-case-version-edit-writes-nothing differ without one question being answered two ways: a leaving writes nothing and so leaves no version to be keyed on, and it returns the curator to the surface the editing was reached from for that reason, while a creation that succeeds leaves the version the curator came to make.

The identity is the case's slug together with the created version's own number because neither alone names what was created. The number is assigned by the counter domain/knowledge/case declares — always higher than every number that case has ever held, including one later discarded, which a-case-version-number-is-never-reused keeps true — so the submission never carried it and no surface can derive it from what the curator typed; the completed creation naming it is the only way the curator learns which version is theirs, the same silence over a stored number a-revise-answers-the-revision-number-it-saved already refused for a hypothesis-revision. The slug alone would name the case rather than the version, and a-cases-current-pins-come-from-its-highest-numbered-version reads a case-keyed surface off whichever version is currently highest, which is a fact about the case's present state rather than a statement that this creation made it.

The version's own surface is also the only destination the two rules already written over this exact moment can hold: a-draft-versions-content-is-presented-only-from-its-own-record states what a surface presenting a newly created draft presents and from which record, and a-newly-created-draft-offers-no-act-before-its-own-record-arrives states what that same surface withholds until that record arrives — both written over a surface reading that one version's own record, which is the reading read-case answers for a slug and a version.

The three refused destinations are refused for reasons this specification already stands on. Staying on the authoring surface makes a submission that succeeded indistinguishable from one not yet made, and the act that surface still offers is a second create-draft over the same case, which a-case-has-at-most-one-draft now refuses outright. The listing of cases answers case summaries a page at a time under constraints/listings-are-paged and in slug order under a-case-listing-answers-cases-in-slug-order, so which page the case falls on is that constraint's answer and not this one's; worse, a-case-summary-is-derived-from-its-existing-versions leaves a case that has never released a version without title, when_to_use or released_version, so the curator would land where the version just created is barely in view. The case's own versions listing is refused on the same paging ground, and nothing is lost by it, since a-listed-case-version-offers-a-route-to-its-own-manifest already owes a route onward from every reading of it.

That the destination's own read may not answer at once, or may not read back as a case at all, costs this landing nothing: a-draft-versions-content-is-presented-only-from-its-own-record and a-newly-created-draft-offers-no-act-before-its-own-record-arrives already state what is presented and withheld while no answer has arrived, and a-case-version-failing-validation-at-a-read-is-refused-by-name, a-case-keyed-surface-states-a-current-version-that-does-not-read-back-as-a-case and a-refusal-a-case-keyed-surface-cannot-name-is-presented-as-a-read-that-did-not-complete already state what the reader is told where the read is refused — so every window of this destination is answered by rules that stand, rather than the destination being chosen to avoid them.

Home is a new rule rather than contracts/knowledge/case-lifecycle, which as an api contract cannot declare a presentation, and rather than domain/knowledge/case-version, which declares what a version is and not what a surface does with one — the same home the two integration landings took. It is an invariant over the case version alone because the version number and the case it references are that element's own declared facts, needing no second aggregate read, exactly as a-revise-answers-the-revision-number-it-saved is held over hypothesis-revision alone. It adds no field, refuses no call, changes no listing and moves no pin.
