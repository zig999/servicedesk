- field: statement
  unstated: Whether a parameter or request-body field the chosen operation declares required, whose own schema does not reduce to one JSON Schema type and which therefore declares no input_schema properties entry and stands in the draft's unresolved list, is still listed in input_schema's top-level required array or left out of it.
  decided: Left out — required lists only those names the operation declares required that hold a properties entry, and a name standing in unresolved with reason schema-not-reducible-to-a-type is named there alone.
  why: domain/integration/capability-schema-draft gives input_schema the shape a-capability-input-schema-holds-a-well-formed-object fixes, where required is a subset of properties' own keys; a required entry naming a key properties does not hold would draft a schema that rule refuses with a 422 at registration, so the draft would be unusable as drafted, while the operation's own requirement of that name still reaches the operator through the unresolved item already carrying it.
- field: statement
  unstated: Whether a parameter, request-body field or response field schema whose oneOf or anyOf names one and the same JSON Schema type among all of its branches reduces to that type or reduces to no type — the reduction reading enumerated a schema stating a type directly, an allOf every branch of which states one and the same type, and a oneOf or anyOf naming more than one type (which reduces to no type), leaving branches that all agree on one type unaddressed.
  decided: 'It reduces to that type: the entry is drafted at that name holding the agreed type, the name is listed in required where the operation declares it required, and it does not stand in the draft''s unresolved list.'
  why: 'Branches that all name one type leave exactly one type to read, so drafting it guesses nothing — it is the same agreement the allOf reading is already decided by, and the unresolved list exists for what the draft genuinely cannot resolve, not for a name whose type every branch of the document agrees on. Deciding the other way would also make the specification''s own standing vocabulary false: both rule Descriptions and domain/integration/capability-schema-draft-unresolved-reason name the non-reducible shape as "a oneOf or an anyOf naming more than one type", a qualification that would have to be withdrawn to refuse an agreeing one. It also costs the operator required standing the operation declares, over an ambiguity the document does not have.'
- field: statement
  unstated: Whether a parameter, request-body field or response field schema that states no type directly and declares no allOf, oneOf or anyOf — an empty or free-form schema, or one carrying only other constraints such as format or description — reduces to one JSON Schema type or to no type; the rule enumerated reduction for a schema stating a type directly, an allOf whose branches share one type, and a oneOf or anyOf naming more than one type only.
  decided: It reduces to no type — such a schema is one that does not reduce, so the name declares no properties entry, is left out of input_schema's required array however the operation declares it required, and stands in the draft's unresolved list with reason schema-not-reducible-to-a-type.
  why: A schema that constrains nothing about type admits every JSON value, so no type is the document's own answer and any entry drafted at that name would state a type the document never gave — the draft would present the operator with an invented fact indistinguishable from a read one, where the unresolved item presents the absence as the absence it is.
