## Description

Reuses the same envelope reading the sibling connector configuration draft's own responseMap already holds, for the same document and the same reason: a schema wrapping its fields in one enveloping property is read through it rather than yielding a single field named after the envelope.
Every success response schema contributes, rather than the lowest one alone, because a field one status carries and another does not is still a field the operation answers with; where more than one declares the same name, the lowest status's own declaration of its type and its required standing is the one kept, the same convention a-connector-configuration-draft-states-a-response-map-from-the-operations-success-response-schemas already reads its own response fields by.
The properties object is drafted even where it holds no entry, so a reviewing operator reads an operation that answers no field as exactly that rather than as a draft that failed silently.
A response field's schema reduces to one type on exactly the reading a-capability-schema-drafts-input-schema-is-read-from-the-chosen-operations-parameters-and-fields already gives a parameter's or a request-body field's own: it states type directly, every branch of an allOf states one and the same type, or every branch of a oneOf or an anyOf names one and the same type; a oneOf or an anyOf naming more than one type does not reduce, a schema stating no type directly and declaring none of those compositions does not reduce either, and the name is disclosed rather than guessed at. domain/integration/capability-schema-draft-unresolved-reason already holds schema-not-reducible-to-a-type over a response field as well as over a parameter and a request-body field, and domain/integration/capability-schema-draft-unresolved-item already holds one response field the draft could not honestly turn into a properties entry; this statement is where the output_schema reading itself says so, rather than leaving a check only the input_schema reading states.
The declaration read for reducibility is the lowest-status one, because that is the declaration the entry's own type would have come from: this rule already keeps the lowest success status's own declaration however differently another success response schema declaring that same name declares it, so a higher status declaring it reducibly leaves the outcome untouched and the name is disclosed rather than drafted from a schema the entry does not read.
A name left unresolved is named in no required array, since a required array naming a property the properties object does not hold would state a demand over a field the draft never drafted.
Required standing is read at the level the name itself was read from, because that is the level its type and its very presence were read from: a name reached through an envelope is required where the enveloping property's own inner object schema lists it in that inner schema's own required array, the only array in the document that ever names it, while the outer success response schema's top-level required array can name the enveloping property alone -- reading required from that outer array would leave every envelope-read field unrequired however plainly the document requires it.
The enveloping property's own name holds no entry in the drafted properties object, so the outer required array naming it requires nothing of the draft; nor is the envelope's own required standing compounded with the field's, since a field required only because its envelope is also required is an inference about presence the document never states, where the draft's business is to hand the operator what one schema declares about one name.
