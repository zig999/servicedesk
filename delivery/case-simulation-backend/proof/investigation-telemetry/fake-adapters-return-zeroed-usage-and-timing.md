## What it is

Fixes the three items the implementation record's own `deferred` section named for this proof to close, and adds no test beyond what those fixes and this task's own three criteria require.

Eight pre-existing tests in `hypothesis-evaluator.port.spec.ts` are rewritten in place rather than deleted: six whose bare `toEqual` omitted usage/elapsed_ms entirely now include the zero-valued pair this task's own criterion 1 requires; the two that specifically proved the depended-upon widen-judgment-and-consolidation-ports task's own now-superseded guarantees (a seeded non-zero usage/elapsed_ms/prompt passed through a call unchanged; the source declaring neither field at all) are replaced with equivalent-strength successors proving this task's own new guarantee instead — a seeded non-zero usage/elapsed_ms is overridden to zero while a seeded prompt still passes through unchanged, and an outcome seeded without a prompt at all answers without one, still carrying the zero-valued usage/elapsed_ms. Every pre-existing test's own fixture-seeding and lookup behavior, and both fakes' own unseeded-key throw, are left exactly as this task's own criterion 3 requires — unchanged — and are proven already by the two pre-existing, untouched tests naming an unseeded criterion/call in `hypothesis-evaluator.port.spec.ts` and `assessment-consolidator.port.spec.ts`, so no new test is written for criterion 3.

Criterion 2 (FakeAssessmentConsolidator's own zero-valued usage/elapsed_ms plus its placeholder prompt) is verified rather than rewritten: `assessment-consolidator.port.spec.ts`'s own pre-existing "answers a placeholder zero-valued usage, an elapsed_ms of 0 and an empty-string prompt, regardless of what text was seeded" test already asserts `usage: {input_tokens: 0, output_tokens: 0}`, `elapsed_ms: 0` and `prompt: ''` against the fake's live source — exactly the values this task's own delivery record states it kept unchanged (only renaming the two constants and rewriting the surrounding comments), so this test remains accurate and no new one is needed for criterion 2.

`diagnose-e2e.spec.ts`'s own `EXPECTED_NARROWED_EVALUATIONS` constant and `diagnose-persistence-deadline-e2e.spec.ts`'s own `buildFakes()` consolidator fixture are both updated: traced against `judgment-stage.ts` (`asEvaluation`'s own `callRecordOf`, which now carries the fake's zero-valued usage/elapsed_ms through onto every `Evaluation` a genuine `evaluate()` call produces) and `run-diagnosis.ts`/`investigation-pipeline.ts` (confirming, in both files, that a real `evaluate()` call happens before `FakeAssessmentConsolidator.consolidate()` is ever reached, and that `consolidate()` in turn runs before persistence in `diagnose-persistence-deadline-e2e.spec.ts`), both fixtures' own seeded evaluations arrays now carry the zero-valued usage/elapsed_ms this task's criterion 1 attaches, in the exact field order `asEvaluation`'s own object-literal spread produces (`hypothesis`, `verdict`, `reason`, `citations`, then the spread-in `usage`, `elapsed_ms`) — since `FakeAssessmentConsolidator`'s own fixture key is a `JSON.stringify` of the whole call, and a key whose field order or content differs throws for a call nothing seeded rather than matching. Without this fix, both e2e tests would fail: `diagnose-e2e.spec.ts`'s request would 500 instead of returning the fixture case's own fallback assessment, and `diagnose-persistence-deadline-e2e.spec.ts`'s own `delayed.wasReached()` assertion would fail (`false` rather than `true`), because the consolidator would throw before persistence's own delaying connection is ever reached — never a genuine confirmation of deadline-exceeded behavior at all.

## Notes

`diagnose-persistence-deadline-e2e.spec.ts`'s own comment marking its consolidator fixture "unreachable" was traced carefully rather than taken at face value, per this task's own instruction: "unreachable" names the seeded text — never returned to the caller, since persistence errors before the response can carry it back — not that the fixture's own key is never matched. `run-diagnosis.ts`'s own `runDiagnosis` calls `runInvestigationPipeline` (collection, judgment, resolve-and-narrow, drafting) to completion before ever calling `writeWithinDeadline`, and this file's own one required hypothesis's evidence is seeded `'ok'`, so `judgeOneHypothesis`'s own no-data pre-check never fires and `evaluate()` — followed by `consolidate()` — both genuinely run before the delayed write is ever attempted. The fixture therefore does need updating, and was updated above; it is not left untouched.

Both e2e fixture fixes and the eight rewritten unit tests are the full extent of what this proof required: this task's own three criteria state a single fixed literal (zero) for usage/elapsed_ms and a plain, unchanged throw for an unseeded key, which the tests above already prove without residual gaps, and the implementation record's own `inferences` (the override-regardless-of-seed behavior, and the prompt-left-untouched behavior) are each proven by name above rather than left to be inferred a second time by a reader of this proof.
